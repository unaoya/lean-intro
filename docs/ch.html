型と命題の対応（Curry–Howard 対応）の雰囲気

Intro1.lean の目標1は「項の型を推測する——それは機械的にできる」だった。このファイルの目標は目標2: その同じ仕組みが、定理の証明の検証にそのまま使えることを納得することである。

Lean には「型の世界」と「命題の世界」があり、この2つはよく似ている。

  • 型 α に対しては、項 a : α を作る。
  • 命題 p に対しては、証明 h : p を書く。

型の世界での基本の活動は項を作ること、命題の世界での基本の活動は証明を書くこと。まず0節で「そもそも証明するとは何をすることか」を具体例で考え直し、 命題に対応する型の項を作ることが証明することだという、このファイルの中心の主張を立てる。そのあと、すでにある型（命題）から新しい型（命題）を作る操作を6つ並べ、それぞれについて、その命題を示すときの書き方と使うときの書き方を見比べる（型の側では「項を作るとき」と「項を使うとき」にあたる。論理学で導入則・除去則と呼ばれる区別だが、この教材では呼び名もこの2語で通す）。対応する項と証明が同じ字面で書けることが繰り返し現れる。

0. 証明するとは何をすることか

Intro1.lean 1節からの積み上げで見たのは、 項の型は機械的に計算・検査できるということだった。このファイルで納得したいのは、次の一つの主張である:

命題に対応する型があり、その型の項を作ることが、その命題を証明することである。

これが納得できれば、話は一気に進む。証明であるべき項の型を検査して、それが元の命題に一致していれば、証明の正しさを機械的に確かめたことになる——検査の手段は、Intro1.lean の型検査そのものだからである。

だがこの主張は、初めて見ると奇妙に響く。証明とは論理をたどる営みで、項とは fun n => n + n のような式だったはずである。なぜ式を作ることが証明になるのか。それを納得するために、まずそもそも証明する、証明を読んで納得するとは何をすることかを、考え直すところから始めたい。

数学の証明は、書かれ、読まれ、読んだ人が「正しい」と納得することで機能する。では、証明を読んで納得するとき、読者は何をしているのだろうか。

こうモデル化できる。読者は文脈——いま使ってよいものの一覧（定理の仮定・既知の定理・ここまでに導いた事実）——を持って読み進める。そして各文で、次のような確認をしている。

  • 「〜とする」「任意に取る」— 新しい変数や仮定を文脈に加える
  • 「A と B より C」— A と B が文脈にあるか、当てはめの条件が合うかを確かめて、C を文脈に加える
  • 「〜となる x を取る」— 文脈にある存在文を分解して、x とその性質を文脈に加える
  • 最後の文 — 示すべきことが、文脈にあるものから組めているかを確かめる

重要なのは、どの確認も局所的だということである。見るのはその一文と現在の文脈だけでよく、証明全体の狙いや発想を理解する必要はない。しかも確認の中身は「一覧にあるか」「形が合うか」の照合であって、機械的に実行できる。直感や洞察が要るのは証明を見つけるときであって、検める作業には要らない。「納得した」とは、この検査がすべての文で通ったことの別名である。

以下、初等的な事実を5つ、この観点で書き直していく。それぞれについて「ふつうの証明」から出発し、省略をすべて書き出した「詳細版」、主張そのものを述語論理で書く「論理式」、各段で何の証明の仕方を名指ししているかを言葉にした「形式化を意識した版」を経て、最後に「Lean の項」に至る。例1・例2では算術の事実を既知の定理として使い、例3ではその「既知」を信用せず自分で証明し、例4・例5では関数の性質を扱う。

例1: どの n についても n + n は偶数

偶数の定義から確認する。「m は偶数」とは「半分になる数がある」、すなわち m = 2k となる k が存在することである。

ふつうの証明。「n + n = 2n だから偶数である。∎」

詳細版。省略をすべて書き出す。

  1. n を任意に取る。
  2. 既知の定理 2n = n + n の左右を入れ替えて、n + n = 2n を得る。
  3. よって「半分」の証人として n が取れ、n + n は偶数である。∎

論理式。証明の構造が見えたところで、主張そのものも形式の言葉に直しておく。「どの自然数 n についても、n + n は偶数である」は、述語論理の論理式では

∀n Even(n + n)

と書ける。述語 Even を定義まで開けば

∀n ∃k (n + n = 2k)

である。日本語の「どの…についても」「…となる—がある」が、量化子 ∀・∃ に置き換わっただけである。形式化と呼ばれる作業には、この主張の形式化と、これから行う証明の形式化の2段階がある——主張の側は、論理式で書けた時点でほぼ済んでいる。

形式化を意識した版。同じ証明を、各段で何の証明の仕方を使っているかを名指ししながら読み直す。

まず n を任意に取り、この固定した n について「n + n は偶数」をこれから証明する——これが全称量化された命題の証明の仕方である。「どの n についても」を示すとは、n を1つ固定して（ただし n について何も仮定せずに）示すことにほかならない。

n を固定したら、偶数の定義に戻る。「m が偶数」とは「ある k が存在して m = 2k となる」ことだった。いまの場合に当てはめると、示すべきは「n + n = 2k となる k が存在する」である。そして存在量化された命題の証明の仕方は、(i) 存在するものの候補を1つ挙げ、(ii) その候補が実際に求められる性質を満たすことの証明を与える——この2つを揃えることである。

ここでは候補として k = n を取ればよい。すると満たすべき性質は n + n = 2n となり、これは成り立つので、証明が完成した。——ただし最後の一歩で、 n + n = 2n を既知の定理として使っていることには注意しておく（この「既知」を信用せず自分で証明するとどうなるかは、例3で掘り下げる）。

使った頭の動きは3つだけである: 全称の証明（任意に取って示す）、 定義に戻る、存在の証明（候補+性質の証明）。

項。これを Lean に持ち込む。まず命題を書く記号を先取りする（それぞれ後の節で主役になる）。命題は Prop 型の項として書けるのだった（Intro1.lean 1節の先取りの回収である）。「どの n についても」は ∀ n, …、「…となる k が存在する」は ∃ k, … と書く。すると主張が、論理式とほぼ字面どおりに対応する形で書ける:

論理式:  ∀n ∃k (n + n = 2k)
Lean:    ∀ n : Nat, ∃ k, n + n = 2 * k

違いは1つだけ——束縛変数の走る範囲が型として明示される（∀ n : Nat）。述語論理では文脈が決めていたものが、Lean では型の仕事になる。 Lean の命題は、型注釈のついた論理式と読んでよい。主張の形式化はこれで済んだ。残るは証明の形式化である。

定理の宣言は theorem で行う——形は def とまったく同じで、コロンの右の「型」の位置に命題を書き、:= の右に証明を書く（theorem の正確な位置づけは次節で述べる）。その証明が、項である:

theorem even_double : ∀ n : Nat, ∃ k, n + n = 2 * k :=
  fun n =>                     -- (1) n を任意に取る
    ⟨n, (Nat.two_mul n).symm⟩  -- (3) 証人は n、(2) 根拠は既知の定理の入れ替え

#check even_double
even_double (n : Nat) : ∃ k, n + n = 2 * k

エラーが出ない＝この項が宣言どおりの型を持つことを機械が確認した、ということである。形式化を意識した版の頭の動きが、そのまま項の部品に写っている:

  • fun n => が「n を任意に取る」——全称の証明は、どの n を渡されても、その n での証明を返す関数になる（Intro1.lean 3節の fun そのもの）。
  • ⟨n, …⟩ が「候補と、性質を満たす証明の組」——存在の証明は組になる（Intro1.lean 5節の ⟨ ⟩ そのもの）。なお、この候補のことを以後証人と呼ぶ。
  • (Nat.two_mul n).symm が「既知の定理を使う」——既知の定理 Nat.two_mul n : 2 * n = n + n は名前のついた完成品の項で、n を渡す 適用の形で取り出す。.symm は等式の左右を入れ替える道具である。

番号にも注意——詳細版の 1→3→2 の順に部品が並び替わっている。 散文は発見の順で書かれ、項は命題の形の順で組まれるのである。

ところで論理式の側では、述語 Even に名前を付けて ∀n Even(n + n) と 略記できた。Lean でも同じことができる——述語を名前のついた定義にすればよい:

偶数であること: 半分になる数が存在する。

def IsEven (n : Nat) : Prop := ∃ k, n = 2 * k

#check IsEven
IsEven (n : Nat) : Prop

主張は ∀ n : Nat, IsEven (n + n) と略記できて——

theorem isEven_double : ∀ n : Nat, IsEven (n + n) :=
  fun n => ⟨n, (Nat.two_mul n).symm⟩

#check isEven_double
isEven_double (n : Nat) : IsEven (n + n)

証明の項は一字も変わらない。IsEven (n + n) と ∃ k, n + n = 2 * k が定義上同じであることは、型検査器が定義を展開して勝手に照合してくれる からである（Map Nat Nat を計算すると Nat → Nat になったのと同じ）。形式化を意識した版の「定義に戻る」に対応する部品が項のどこにもないのは、このためである。以後は略記した IsEven の側を使う。

例2: 偶数と偶数の和は偶数

ふつうの証明。「n = 2k、m = 2l と書けば n + m = 2k + 2l = 2(k + l)。∎」

詳細版。

  1. n, m を任意に取り、hn「n は偶数」・hm「m は偶数」を仮定する。
  2. hn から、n = 2k となる k を取り、この等式を hk と名付ける。
  3. hm から同様に l を取り、等式を hl と名付ける。
  4. hk の両辺に右から m を足して、n + m = 2k + m。
  5. hl の両辺に左から 2k を足して、2k + m = 2k + 2l。
  6. 分配法則より 2k + 2l = 2(k + l)。4〜6 を = のつながりとして読めば n + m = 2(k + l)。
  7. よって証人 k + l により、n + m は偶数である。∎

論理式。主張は

∀n ∀m (Even(n) → Even(m) → Even(n + m))

——n と m の全称量化の内側に、「ならば」（→）が2つ並ぶ形である（Even(n) ∧ Even(m) → … と「かつ」でまとめても同値だが、仮定を1つずつ取る詳細版の読みには、→ の並びのほうが対応する）。

形式化を意識した版。今度は仮定つきの命題である。「…ならば—」の証明の仕方は、仮定を取って（名前を付けて）結論を示すこと——全称のときの「n を取る」と同じ頭の動きである。

仮定 hn を使う番になったら、また定義に戻る。hn は「n = 2k となる k が存在する」ことの証明である。存在量化された命題の使い方は、証明の仕方のちょうど逆で、存在するものを1つ取り出して名前を付ける——「k をそういう数とする。以後 hk : n = 2 * k が使える」と宣言する動きである。hm からも同様に l と hl を取り出す。

示すべきは（定義に戻ると）「n + m = 2j となる j の存在」。候補は j = k + l で、満たすべき性質は n + m = 2(k + l) である。この等式は一度には出ないので、 等式の連鎖で作る: hk の両辺に同じ操作 (· + m) を施して n + m = 2k + m、 hl から同様に 2k + m = 2k + 2l、分配法則（既知の定理）で 2k + 2l = 2(k + l)、最後に3本の等式をつなぐ。ふつうの証明で「= を続けて書く」ことの正体は、この「両辺に同じ操作」と「つなぐ」の繰り返しである。

項。「取り出して名前を付ける」は、Intro1.lean 4節の match をパターン ⟨k, hk⟩ で使えばよい——存在の証明は「証人と根拠の組」だから、組と同じようにほどける。「両辺に同じ操作」は congrArg、「つなぐ」は .trans という名前の道具である（(· + m) は fun x => x + m の略記。 (2 * k + ·) なら fun x => 2 * k + x）。道具の型を先に挙げておく——以下の照合はこの3つの型と適用規則だけでできる（表示中の Sort u_1 は Prop と Type を束ねる宇宙の表記で、ここでは Type か Prop と読めばよい）:

@congrArg : ∀ {α : Sort u_1} {β : Sort u_2} {a₁ a₂ : α} (f : α → β),
            a₁ = a₂ → f a₁ = f a₂
@Eq.trans : ∀ {α : Sort u_1} {a b c : α}, a = b → b = c → a = c
Nat.mul_add : ∀ (n m k : Nat), n * (m + k) = n * m + n * k
theorem isEven_add {n m : Nat} (hn : IsEven n) (hm : IsEven m) : IsEven (n + m) :=
  match hn, hm with
  | ⟨k, hk⟩, ⟨l, hl⟩ =>                     -- (2)(3) 取り出して名前を付ける
    ⟨k + l,                                  -- (7) 証人と、つないだ根拠
     ((congrArg (· + m) hk).trans            -- (4) 両辺に (· + m)、(6) つなぐ
        (congrArg (2 * k + ·) hl)).trans     -- (5) 両辺に (2 * k + ·)、(6) つなぐ
        (Nat.mul_add 2 k l).symm⟩            -- (6) 分配法則（既知の定理）

#check isEven_add
isEven_add {n m : Nat} (hn : IsEven n) (hm : IsEven m) : IsEven (n + m)

仮定 hn・hm が引数になっていることに注意——「ならばの証明=仮定を取る」も、項では fun と同じ扱いである（詳細版の (1) は引数の宣言に吸収されている）。主張全体も論理式 ∀n ∀m (… → … → …) の写しである: 定理の引数の列は∀ と → を Intro1.lean 3節の binder 形式で書いたもので、n・m は値から決まるため暗黙引数 { } になっている。

もう1つ、形式化を意識した版で付けた名前 h1〜h3 は、項では式の入れ子に吸収されている——名前は考えの整理のための道具であって、証明の実体は式である。コメントの番号で詳細版と対応づけたので、読みにくければ番号の順に内側から組み立て直しながら読むとよい。例1と同じく、散文は発見の順、項は命題の形の順である。

補足（初読は飛ばしてよい）: 途中の項の型を確かめる

連鎖の途中——たとえば (4) と (5) をつないだところ——の型も #check で確かめられる。等式の証明に h1・h2 と名前を付けた文脈を、既習の fun で用意すればよい:

#check fun (n m k l : Nat)
    (h1 : n + m = 2 * k + m)
    (h2 : 2 * k + m = 2 * k + 2 * l) =>
  h1.trans h2
fun n m k l h1 h2 ↦
  Eq.trans h1 h2 : ∀ (n m k l : Nat), n + m = 2 * k + m → 2 * k + m = 2 * k + 2 * l → n + m = 2 * k + 2 * l

出力全体は fun で作った関数の型であり、最後の n + m = 2 * k + 2 * l が、この文脈での h1.trans h2 の型である。その右辺は h3 の左辺と一致するので、さらに .trans h3 とつなげて n + m = 2 * (k + l) を得る。

例3: 掘り下げ — 「既知」だった 2n = n + n を自分で証明する

例1で使った Nat.two_mul を、今度は信用せずに自分で証明してみる。

ふつうの証明。「n についての帰納法で明らか。∎」

詳細版。

  1. n = 0 のとき: 両辺とも 0。
  2. n = k + 1 のとき: k での等式 2k = k + k が使えるとする。 2(k + 1) = 2k + 2 = (k + k) + 2 = (k + 1) + (k + 1)。∎

論理式。主張は

∀n (2n = n + n)

——量化子1つと等式だけの、いちばん簡素な形である。今回は述語の略記も要らない。

形式化を意識した版。全称の証明の仕方には、「任意に取る」のほかにもう1つ、自然数に固有の方法がある——帰納法である: 0 の場合を示し、「k で成り立つならば k + 1 でも成り立つ」を示す。

0 の場合、示すべき 2·0 = 0 + 0 は両辺とも計算すれば 0 になる。計算で一致する等式には、それ以上の証明は要らない。k + 1 の場合のポイントは、 帰納法の仮定 2k = k + k を「既知の定理」と同じ資格で使ってよいこと——あとは例2で覚えた等式の連鎖である。

ただし、連鎖の途中の1歩「(k + 1) + k = (k + k) + 1」が、また別の「既知」（succ_add と呼ばれる事実）を呼んでしまう。信用しないと決めたので、 これも同じ流儀（帰納法）で証明する。今度の各段は計算と「両辺に + 1」だけで閉じ、新しい既知はもう現れない——底に着いた。

項。帰納法は、Intro1.lean 4節の再帰 そのものとして書ける。「k での場合の証明」は、自分自身の再帰呼び出しで手に入る（toN の再帰と同じ形である。また、計算で一致する等式の証明は rfl と書く——次節で解剖する）:

theorem succ_add' : ∀ (n m : Nat), (n + 1) + m = (n + m) + 1 := fun n m =>
  match m with
  | 0     => rfl                                  -- 両辺とも計算で n + 1
  | j + 1 => congrArg (· + 1) (succ_add' n j)     -- 帰納法の仮定は再帰呼び出し

theorem two_mul' : ∀ n : Nat, 2 * n = n + n := fun n =>
  match n with
  | 0     => rfl
  | k + 1 =>
    (congrArg (· + 2) (two_mul' k)).trans          -- 2(k+1) = 2k+2 = (k+k)+2
      ((congrArg (· + 1) (succ_add' k k)).symm :
        (k + k) + 2 = (k + 1) + (k + 1))           -- 型注釈は詳細版の式変形の写し

#check two_mul'
two_mul' (n : Nat) : 2 * n = n + n

どこまで掘っても、現れたのは同じ仕組みで書かれた項だけだった。それを機械に確認させることもできる:

#print axioms two_mul'
'two_mul'' does not depend on any axioms

例1で「既知」と呼んだものは信用ではない——底（定義と計算）まで、すべて検査済みの項なのである。

例4: 単射どうしの合成は単射

ふつうの証明。「g (f x) = g (f y) とすると、g の単射性より f x = f y。 f の単射性より x = y。∎」

詳細版。

  1. x, y を任意に取り、h : g (f x) = g (f y) を仮定する。
  2. 仮定 hg は「どんな u, v についても、g u = g v ならば u = v」という全称文である。u := f x、v := f y と特殊化して h に適用し、f x = f y を得る。
  3. hf を同様に f x = f y に適用して、x = y。これが示すべきことだった。∎

論理式。示すべき結論「合成 g∘f が単射」を、単射の定義まで開くと

∀x ∀y (g(f(x)) = g(f(y)) → x = y)

である。仮定 hg・hf も同じ形の論理式（∀u ∀v (g(u) = g(v) → u = v) など）であることが、この例の主役になる。

形式化を意識した版。論理式で書いたとおり、示すべきは全称と「ならば」の重なった命題である。だから頭の動きは「x, y を取り、さらに仮定 h を取る」。

今度は、仮定 hg・hf の使い方が主役になる。hg 自身が全称+ならばの命題、つまり「当てはめて使う道具」である。全称文・ならば文の使い方は、対象を当てはめて適用すること——例1の「既知の定理 Nat.two_mul を n に適用」と、実は同じ動きである。仮定も既知の定理も、文脈にある部品という資格は変わらない。

項。まず、論理式をそのまま型にして証明する（仮定 hg・hf も単射の定義を開いた論理式の形で書く）:

example {α β γ : Type} {f : α → β} {g : β → γ}
    (hg : ∀ u v, g u = g v → u = v) (hf : ∀ u v, f u = f v → u = v) :
    ∀ x y, g (f x) = g (f y) → x = y :=
  fun x y h => hf x y (hg (f x) (f y) h)

「取る」が3連続の fun x y h——全称も「ならば」も、項では同じ関数である。そして「〜の単射性より」という紙の一語が、適用 hg (f x) (f y) h そのものになる。詳細版で意識した特殊化（u := f x、v := f y）を、ここでは引数として自分の手で書いている。

単射のような頻出の性質には、ライブラリが名前のついた述語を用意している—— Function.Injective f である（例1の IsEven と同じ、略記の発想）。これで書き直すと:

theorem comp_injective {α β γ : Type} {f : α → β} {g : β → γ}
    (hg : Function.Injective g) (hf : Function.Injective f) :
    Function.Injective (fun x => g (f x)) :=
  fun x y h => hf (hg h : f x = f y)

#check comp_injective
comp_injective {α β γ : Type} {f : α → β} {g : β → γ} (hg : Function.Injective g) (hf : Function.Injective f) :
  Function.Injective fun x ↦ g (f x)

主張が略記で縮んだだけでなく、証明からは特殊化 (f x)・(f y) も消えて hg h だけになった。Function.Injective は点の引数を暗黙引数 （{ } の変種 ⦃ ⦄。ここでは同じものと読んでよい）として宣言しているので、機械が埋めてくれるからである（型注釈 : f x = f y は「f x = f y を得る」という文の写しで、消しても通る）。

例5: 全射どうしの合成は全射

ふつうの証明。「c を取る。g の全射性より g b = c となる b があり、 f の全射性より f a = b となる a がある。すると g (f a) = g b = c。∎」

論理式。示すべき結論「合成 g∘f が全射」は、定義まで開くと

∀c ∃a (g(f(a)) = c)

——例1と同じ「∀ の内側に ∃」の形が、関数の文脈で再登場する。

形式化を意識した版（今回は詳細版を兼ねる。ここまでの動きの総復習である）。 c を任意に取る（全称の証明）。全射の定義「どの点にも、そこへ送られてくる元がある」に戻ると、hg c は「g b = c となる b の存在」の証明——存在の使い方で b と hb を取り出す（例2）。hf b からも a と ha を取り出す。示すべきは「g (f a) = c となる a の存在」だから、候補 a と性質の証明を組にする（例1）。性質 g (f a) = c は等式の連鎖で: ha の両辺に g を施して g (f a) = g b、 hb とつなぐ（例2）。∎

項。まず論理式をそのまま型に（仮定も全射の定義を開いた形で書く）:

example {α β γ : Type} {f : α → β} {g : β → γ}
    (hg : ∀ c, ∃ b, g b = c) (hf : ∀ b, ∃ a, f a = b) :
    ∀ c, ∃ a, g (f a) = c :=
  fun c =>
    match hg c with
    | ⟨b, hb⟩ =>
      match hf b with
      | ⟨a, ha⟩ => ⟨a, (congrArg g ha).trans hb⟩

ライブラリの述語 Function.Surjective で略記して書き直すと—— 証明の項は一字も変わらない（定義上同じ命題だからである。例1と同じ）:

theorem comp_surjective {α β γ : Type} {f : α → β} {g : β → γ}
    (hg : Function.Surjective g) (hf : Function.Surjective f) :
    Function.Surjective (fun x => g (f x)) :=
  fun c =>
    match hg c with
    | ⟨b, hb⟩ =>
      match hf b with
      | ⟨a, ha⟩ => ⟨a, (congrArg g ha).trans hb⟩

#check comp_surjective
comp_surjective {α β γ : Type} {f : α → β} {g : β → γ} (hg : Function.Surjective g) (hf : Function.Surjective f) :
  Function.Surjective fun x ↦ g (f x)

例4と並べると対になっている: 単射は fun と適用だけの世界、全射は取り出しと組の世界。そして入れ子の match は、「b を取り出したあとの世界で a を取り出す」という証明の依存関係を、形として見せている。

主張は論理式に（そして型注釈を付ければそのまま Lean の型に）、証明は「ふつうの証明 → 詳細版 → 形式化を意識した版 → 項」へと磨かれた。進むにつれて増えたのは省略の穴埋めだけで、新しい種類の思考は何も足していない。形式化とは翻訳ではなく、詳細化の極限である。

証明を読んで納得するとは、冒頭のモデル化のとおり、有限種類の動きが正しく行われていることを一文ずつ検査することだった。各動きは項の部品に写り、その検査は項の型検査に写る。そして、詳細版の各文に読者が行う局所的な照合——「文脈にあるか」「形が合うか」——を、一行も飽きず、一箇所も「まあいいか」と流さずに実行するものこそ、型検査器である。冒頭の主張——命題に対応する型の項を作ることが証明することである——は、この表を信じるなら、もう奇妙には響かないはずである。

残りの節は、この表を精密化する。1節で最小の例（1 + 1 = 2）を解剖し、2〜7節で「ならば・かつ・または・矛盾・すべての・存在する」を型の世界と1対1に対応させ、 8節でまとめの対照表を作る。 9節では = や ≤ という命題そのものが帰納型で作られていることまで掘る。そのうえで10節が、冒頭の主張の回収——「型検査が証明の検査になる」——である。（まだ出ていない動きも少数ある——「または」の場合分けなどは対照表の節で揃う。）

1. 準備 — 命題・theorem・rfl

対照表に入る前に、命題の世界の書き方を最小限そろえる（Intro1.lean は型の世界に集中し、命題の話をこのファイルまで持ち越した）。

Intro1.lean の1節で見たとおり、命題は Prop という型を持つ項である。命題を作る記号 = や < も記法だが、裏の仕組みは異なる: = はどの型でも使える1つの述語 Eq の記法であり、 < は + と同じ仲間で、型ごとにクラスの仕組みで意味が決まる（クラスの仕組みそのものは Intro2.lean で説明する）。

  • = < — ざっくり: Nat の上では、どちらも Nat → Nat → Prop という型の関数とみなせばよい。1 + 1 : Nat と 2 : Nat を渡すから 1 + 1 = 2 : Prop。 正確には: = はどの型でも使える Eq : α → α → Prop（α は両辺の型から決まる暗黙引数。定義そのものは9節で見る）、< は型ごとに登録簿で意味が決まる演算である。

2 < 1 のような偽の命題も、命題としては立派な項である。真であるとは「その命題の証明がある」ことである。

命題も型だから、def とまったく同じ構文で「証明という項に名前を付ける」宣言が書ける。型の位置に命題を、:= の右にその証明を書く。このとき def の代わりに theorem と書くのが慣例である。この教材が注目する「型を指定して項に名前を付け、型検査を受ける」という枠組みでは、theorem は def と同じものと考えてよい（正確には違いもある: theorem の中身は定義として展開・計算される対象にはならない、など）。

theorem one_add_one : 1 + 1 = 2 := rfl

この1行の解剖: one_add_one が名前、1 + 1 = 2 が型（＝命題）、 rfl が項（＝証明）である。def 名前 : 型 := 項 とまったく同じ配置である。

#check one_add_one
one_add_one : 1 + 1 = 2

rfl は「両辺が定義から計算して一致する」ことを理由にする等式の証明である（なぜこれが証明と言えるのかは、9節で Eq の定義とともに見る）。 rfl 単体の型も #check rfl で見られる——表示は rfl.{u} {α : Sort u} {a : α} : a = a、つまり「任意の a について a = a の証明」である（Sort の読み方は Intro2.lean で）。

ここで型検査が何をしたかに注意。「項 rfl の型は命題 1 + 1 = 2 と一致するか」という Intro1.lean 2節以来の検査が、そのまま証明の検査になっている。この見方を本格的に展開するのが、このファイルの仕事である。

2. 関数型と「ならば」

示すとき: fun x => e で作る。x : α を仮に置いて e : β を作れば α → β が得られる。「p を仮定すれば q が示せる」なら p → q が言える、というのと同じ形。

使うとき: f a と適用する。関数に項を与えれば値が出る。含意に証明を与えれば結論の証明が出る。

作るとき（型側）: β の項が1つあれば、α から β への関数が作れる。

def constFun {α β : Type} (b : β) : α → β := fun _ => b

#check constFun
constFun {α β : Type} (b : β) : α → β

示すとき（命題側）: q の証明が1つあれば、p → q が示せる。字面はまったく同じ。

theorem constImp {p q : Prop} (hq : q) : p → q := fun _ => hq

#check constImp
constImp {p q : Prop} (hq : q) : p → q

constFun と見比べてほしい。{α β} が {p q} に変わった以外、引数の並びも結果の形も、そのまま重なっている。

使うとき（型側）: 適用。

def applyFun {α β : Type} (f : α → β) (a : α) : β := f a

#check applyFun
applyFun {α β : Type} (f : α → β) (a : α) : β

読み:「f に a を適用して f a」。

使うとき（命題側）: 適用。これも字面が同じ。

theorem applyImp {p q : Prop} (h : p → q) (hp : p) : q := h hp

#check applyImp
applyImp {p q : Prop} (h : p → q) (hp : p) : q

これも applyFun と同じ形である。読み:「定理（含意の証明 h）に仮定の証明 hp を適用して、結論の証明を得る」——数学の「〜より」の正体である。

-- ここまで型側を `def`、命題側を `theorem` で書いたが、どちらの宣言も
-- 「コロンの右に書いたものを持つ項を、`:=` の右に差し出す」という同じ形をしている。
-- `theorem` とは「命題という型の項（＝証明）を作る `def`」にほかならない。
-- 以下のすべての対でも、この形は変わらない。

示すとき: ⟨a, b⟩ で作る。両方の成分を揃えれば組が作れる。 p の証明と q の証明を揃えれば p ∧ q の証明になる。

mkProd {α β : Type} (a : α) (b : β) : α × β

mkAnd {p q : Prop} (hp : p) (hq : q) : p ∧ q

4. 直和型と「または」

示すとき: .inl か .inr のどちらかで作る。左右どちらかの成分があればよい。 p の証明があれば p ∨ q が言えるし、q の証明でもよい。

inlSum {α β : Type} (a : α) : α ⊕ β
theorem inlOr {p q : Prop} (hp : p) : p ∨ q := .inl hp

#check inlOr

5. 空の型と「⊥」

項が1つもない型が Empty、証明が1つもない命題が False。

示すとき: 手段がない。これが空であることの意味そのもので、作り方が用意されていないから項（証明）が存在しない。

使うとき: 場合分けすべき場合が1つもないので、「もし項が手に入ったなら何でも作れる」という形になる。矛盾からは何でも従う、というのと同じ。

型側: Empty の項があれば何の型の項でも作れる。

def elimEmpty {α : Type} : Empty → α := fun e => e.elim

#check elimEmpty
elimEmpty {α : Type} : Empty → α

命題側: 矛盾からは何でも従う。

theorem elimFalse {p : Prop} : False → p := fun h => h.elim

#check elimFalse
elimFalse {p : Prop} : False → p

否定 ¬p は p → False のことなので、実は新しい作り方ではない。

theorem notIntro {p : Prop} (h : p → False) : ¬p := h

#check notIntro
notIntro {p : Prop} (h : p → False) : ¬p

Prelude での定義 — Prop に住む帰納型

実は Empty も False も、Prelude で帰納型として定義されている:

inductive Empty : Type

inductive False : Prop

どちらも構成子ゼロ——「作り方なし」を宣言そのもので表している。違いは住所だけで、 Empty は Type の住人、False は Prop の住人である。つまり False は「項が作れない＝証明できない」命題である。このように、 帰納型は Prop に住む型＝命題も作れる。Prop の世界では、構成子は「その命題の証明の作り方」と読める。

一点側の対応物もある。Unit（構成子1つ・引数なしの型、Intro1.lean 4節）に対応する命題が True である:

inductive True : Prop where
  | intro : True

構成子 True.intro がそのまま証明——「項が作れる＝証明できる」、 True はいつでも証明できる自明な命題である。そして、構成子が複数ある命題の代表が、4節で見た「または」Or だった（inl/inr の2通りの証明の作り方を持つ）。

まぎらわしいが、true : Bool と True : Prop は別物なので注意。 true は計算で使うデータ（Bool は Type の住人）であり、 True は命題（Prop の住人）である。

✏ 練習

  1. theorem noContra {p q : Prop} : p → ¬p → q を書け。ヒント: ¬p は p → False なので、適用すると False が出る。あとは .elim。

6. 依存積と「すべての」

関数型 α → β を一般化して、行き先の型が入力ごとに変わってよいことにしたのが依存積 (a : α) → P a。P : α → Type は「α の各点に型を割り当てるもの」。

命題側で対応するのは全称量化 ∀ a, Q a。 Q : α → Prop は「α の各点に命題を割り当てるもの」で、形はまったく同じ。

示すとき・使うとき: 関数のときと変わらず fun x => e と f a。 α → β は P が定数のときの特別な場合なので、これは自然なこと。

使うとき（型側）: 点 a を与えると P a の項が出る。

具体例: 述語と全称命題

Q : α → Prop——命題を返す関数——は、数学でいう述語である。 Intro1.lean 3節で「型を返す関数」Map を見たのと同じ要領で、具体的に1つ作ってみる:

「すべての n について…」の証明は、依存関数そのものである:各 n を受け取って、命題 IsZero (n * 0) の証明を返す関数を書けばよい。

#check all_mul_zero

証明が fun _ => rfl で済むのは、IsZero (n * 0) が定義上 n * 0 = 0 で、 n * 0 が計算で 0 になるからである（1節の 1 + 1 = 2 と同じ理屈）。

補足（初読は飛ばしてよい）: 対称に見えて rfl が通らない 0 * n

同じ調子で ∀ n, IsZero (0 * n) も書きたくなるが、こちらは通らない:

error: Type mismatch
  rfl
has type
  ?m.10 = ?m.10
but is expected to have type
  IsZero (0 * n)

理由は * の定義が第2引数についての再帰であること。n * 0 は第2引数が 0 なので計算が1歩で進むが、0 * n は第2引数が変数のまま なので計算が止まり、0 * n と 0 は「計算で一致」しない。数学では対称に見える2つの式が、定義のレベルでは非対称なのである（練習2の 0 * 5 が通るのは、5 が具体的な数字で計算が最後まで走るから）。

変数 n のまま示すには n についての数学的帰納法が要る。Lean では帰納法は再帰で書く——実物は Top.lean の mem_interFin などで見る。ライブラリではこの命題（の中身）は Nat.zero_mul として証明済みである。

7. 依存和と「存在する」

直積 α × β を一般化して、第二成分の型が第一成分に依存してよいことにしたのが依存和 (a : α) × P a（P : α → Type、型の族）。命題側で対応するのが存在量化 ∃ a, Q a（Q : α → Prop、命題の族）。

示すとき: ⟨a, b⟩。「どの点か」と「その点で成り立つこと」を組にする。存在を示すには、実際に点を1つ挙げて、それが条件を満たすことを言えばよい、というのと同じ。

使うとき: 組を分解する。型側は .1 .2 で取り出せる。命題側にはここだけ制限があるので、後の 11 節で見る。

9. 例: 自然数の命題を構成子で証明する

「命題を証明する＝項を作る」——つまり、命題に対応する型の項を作れれば、証明できたと思ってよい——を、自然数のいちばん基本的な命題で確かめておく。鍵は、= や ≤ といった命題を作るもの自体が、Intro1.lean の MyNat などと同じく帰納型として定義されていることである。

等しさ Eq

a = b は Eq a b の記法で、Eq は構成子を1つだけ持つ帰納型である:

inductive Eq {α : Sort u} : α → α → Prop
  | refl (a : α) : Eq a a

構成子 refl が作れるのは、両辺が同じ Eq a a の形の項だけ。「a = a はいつでも証明できて、それが等しさの証明のすべて」というのが、等しさの定義そのものになっている。

example : 0 = 0 := Eq.refl 0
example : 0 = 0 := rfl        -- 略記。引数の `0` は型 `0 = 0` の側から決まる

一方 0 = 1 という型の項は refl では作れず、実際この型に項は存在しない。証明のない命題は、項のない型 Empty（5節）と同じ立場にある。

0 節で 1 + 1 = 2 が rfl で証明できたのは、型検査が両辺を 計算してから比べるからである。1 + 1 は計算すると 2 になるので、 1 + 1 = 2 は 2 = 2 と同じ型であり、refl の射程に入る。

順序 Nat.le

m ≤ n も帰納型の記法で、こちらは構成子が2つある:

inductive Nat.le (n : Nat) : Nat → Prop
  | refl : Nat.le n n
  | step {m} : Nat.le n m → Nat.le n (succ m)   -- `succ m` は `m + 1`

作り方は「n ≤ n」と「n ≤ m が作れているなら n ≤ m + 1 も作れる」の2通り。つまり ≤ の証明は、refl から出発して step を必要な回数だけ重ねた項である。 zero に succ を重ねて自然数を作るのと、まったく同じ手つきで証明が作れる。

example : 0 ≤ 0 := Nat.le.refl
example : 0 ≤ 1 := Nat.le.step Nat.le.refl
example : 0 ≤ 2 := Nat.le.step (Nat.le.step Nat.le.refl)

これが8節の主張の実演である。0 ≤ 2 を証明するとは、帰納型 Nat.le の項を構成子から組み立てることに他ならず、出来上がった証明はデータと同じ資格でそこにある。∧ ∨ ∃ False も同様に帰納型として定義された命題であり（3〜5節、7節）、示すときに使った ⟨_, _⟩ や .inl は、それらの構成子だったのである。

等式の法則は公理ではない

ふつうの述語論理では、等式の反射律や代入原理は論理に組み込まれた公理である。 Lean では違う。いま見たとおり Eq はただの帰納型の宣言で、等式に期待される振る舞いは、そこから実際に出てくる:

  • 反射律は構成子 refl そのもの
  • 代入原理（a = b なら、P a の証明から P b の証明が得られる）は、帰納型の宣言を受理したときに Lean が自動生成する帰納法原理 Eq.rec そのもの
  • 対称律・推移律・合同性は、そこから証明される定理
#print axioms Eq.symm
'Eq.symm' does not depend on any axioms

「公理に一切依存していない」という報告——対称律は、帰納型の仕組みだけから 証明された定理である。

つまり Lean の基礎にあるのは等式の公理のリストではなく、「（健全性の条件を満たす）帰納型の宣言に対して、構成子・帰納法原理・計算規則を与える」という一般規則のほうである。等式に限らず、この教材に出てくる ∧ ∨ ∃ = ≤ の論理法則はすべて、依存関数型・宇宙・帰納型という土台から定義と定理として出てくる。

例外として土台の外から公理を足すこともあるが、この教材の主定理が実際に依存するのは、外延性・選択・商型の健全性にあたる3つだけである。それは Top.lean の末尾で #print axioms により確認する。

「全部」と「別々」も出てくる

Intro1.lean 4節で、帰納型の宣言は2つのことを保証すると述べた:構成子で作られたものが項の全部であること、そして違う作り方をした項は 別々であることである。この2つも公理ではなく、同じ一般規則から出てくる。

「全部」の保証の正体は、自動生成される帰納法原理そのものである。 rec は「各構成子の場合を与えれば、すべての項について定義・証明したことになる」と言っており、match の場合分けがそれで尽くせるのはこれによる。

補足（初読は飛ばしてよい）: 構成子が別々であることと noConfusion

「別々」には、これも宣言の受理時に自動生成される道具 noConfusion が使える。「違う構成子どうしは等しくない」と「同じ構成子なら中身まで等しい（構成子は単射）」の両方がこれで証明できる。実物を Bool と Nat で見る（a ≠ b は ¬(a = b) の記法。初出である）:

example : true ≠ false := fun h => Bool.noConfusion h

example {m n : Nat} (h : Nat.succ m = Nat.succ n) : m = n :=
  Nat.noConfusion h (fun h' => h')

#print axioms Bool.noConfusion
'Bool.noConfusion' does not depend on any axioms

noConfusion 自体も公理には依存していない——帰納型の仕組みから 証明された定理である。種明かしだけ述べると、「構成子を match で見分けて True／False を割り当てる述語」を作り、Eq.rec（代入原理）で true = false の仮定からゴール False へ運ぶ——どれも既出の道具である。

補足（初読は飛ばしてよい）: 等式をもう1つ作る実験

Eq が特別な組み込みでないことは、実際に作り直してみるとよく分かる。同じ形の帰納型 MyEq を宣言すると、帰納法原理も同じ形で自動生成される。

inductive MyEq {α : Type} (a : α) : α → Prop where
  | refl : MyEq a a

#check MyEq
MyEq {α : Type} (a : α) : α → Prop

対称律は場合分け（match）だけで導ける。構成子は refl の1つ、つまり a と b が同じ場合しかないので、返すべきものも refl で足りる。推移律や代入原理も同様である。

theorem MyEq.symm {α : Type} {a b : α} (h : MyEq a b) : MyEq b a :=
  match h with
  | .refl => .refl

#check MyEq.symm
MyEq.symm {α : Type} {a b : α} (h : MyEq a b) : MyEq b a

なぜこの match が通るのか——添字の単一化

（ここはこの補足の中でも特に細かい話である。飛ばして、次の example へ進んでよい。）

上の証明をよく見ると、不思議なことが起きている。ゴールは MyEq b a なのに、返しているのは .refl——その型は MyEq a a であって、a と b は別の変数のはずである。なぜ型が合うのか。

鍵は、MyEq の宣言のコロンの左右の違いにある。(a : α) は パラメータ（どの構成子でも共通・固定）、コロンの右の α → Prop の引数は 添字（構成子ごとに値を決められる）である。MyEq a は「各 b に命題 MyEq a b を割り当てる族」だが、唯一の構成子 refl は、この族のうち 対角線 MyEq a a にしか項を作らない。

ここで Intro1.lean 4節の原則——帰納型の項は、構成子で作られたものがすべて——を当てはめる。手元には h : MyEq a b という項がある。項はすべて構成子から作られ、構成子は refl だけで、refl が作る項の型は MyEq a a。したがって、MyEq a b に項があるということ自体が、b は実は a だったことを意味する。

添字つきの型への match は、この推論を実行している。枝に入るとき、「どの構成子か」の列挙（Signal のときと同じ仕事）に加えて、「その構成子で作られたのなら添字は何でなければならないか」の照合（単一化）が走る。 refl の枝の中では b := a と特殊化された世界になり、ゴール MyEq b a は MyEq a a に書き換わる——だから右辺の .refl が受理される。

このことはコンパイル結果に現れる:

#print MyEq.symm
theorem MyEq.symm : ∀ {α : Type} {a b : α}, MyEq a b → MyEq b a :=
fun {α} {a b} h ↦
  match b, h with
  | .(a), MyEq.refl => MyEq.refl

内部では b も一緒にマッチされていて、そのパターンが .(a) になっている。この .( ) は強制パターン——「ここは自由な場合分けではない。h が refl である以上、a であることが強制されている」という印である。

正体まで降りると、これは自動生成された帰納法原理の仕事である:

#check @MyEq.rec
@MyEq.rec : {α : Type} →
  {a : α} → {motive : (a_1 : α) → MyEq a a_1 → Sort u_1} → motive a ⋯ → {a_1 : α} → (t : MyEq a a_1) → motive a_1 t

読み: 「すべての添字 a_1 と t : MyEq a a_1 について motive a_1 t」を結論するのに、要求される義務は refl の場合の motive a ⋯ ただ1つである。「refl の場合だけ示せばよい」という形の中に、「そのとき添字は a」がすでに織り込まれている。match を使わず、この帰納法原理を直接使っても書ける:

theorem MyEq.symm' {α : Type} {a b : α} (h : MyEq a b) : MyEq b a :=
  MyEq.rec (motive := fun c _ => MyEq c a) MyEq.refl h

まとめると: Signal の match は場合の列挙だけだったが、添字つきの族への match は枝ごとに添字の情報が増える（依存パターンマッチと呼ばれる）。「等式で場合分けすると、両辺を同じものとして扱えるようになる」——これこそが Eq の帰納法原理 Eq.rec（代入原理）の中身であり、Top.lean 1節で見る rw が裏でやっていることの正体でもある。

型検査が両辺を計算してから比べる仕組みも Eq 専用ではないので、 1 + 1 = 2 に当たる命題はやはり構成子だけで証明できる。

example : MyEq (1 + 1) 2 := .refl

しかも、Eq と同値であることを系の中で証明できる。 p ↔ q（同値、\iff と打つ）はここが初出だが、これも「p → q の証明と q → p の証明の組」という2フィールドの structure にすぎず、 ⟨→の証明, ←の証明⟩ で作れる。両方向とも「相手の等式で場合分けして、自分の構成子を置く」だけである。なお2つ目の match h with | rfl => … の rfl は、証明項ではなくパターンの位置にある——「Eq の唯一の構成子 Eq.refl の場合」を表す書き方である。

theorem myEq_iff_eq {α : Type} {a b : α} : MyEq a b ↔ a = b :=
  ⟨fun h => match h with | .refl => rfl,
   fun h => match h with | rfl => .refl⟩

#check myEq_iff_eq
myEq_iff_eq {α : Type} {a b : α} : MyEq a b ↔ a = b

propext : (p ↔ q) → p = q（命題の外延性。Top.lean の3公理の1つ）まで使えば、同値であるにとどまらず、命題として等しいことになる。

example {α : Type} {a b : α} : MyEq a b = (a = b) := propext myEq_iff_eq

つまり2つ目の等式を作っても、衝突も分裂も起きず、同じものが増えるだけである。実際 h : MyEq a b を「a = b が証明できた」と解釈しても問題ない——上で示した同値 myEq_iff_eq が、その読み替えの正当化である。 Eq に残る特別さは論理の側にはなく、道具立ての側にある: = という記法や、rw・simp などのタクティク（Top.lean 1節で登場する、証明のもう1つの書き方の道具）は Eq に向けて作られているので、 MyEq では使えない。例えば h : MyEq a b で rw [h] とすると

error: Invalid rewrite argument: Expected an equality or iff proof
or definition name, but `h` is a proof of
  MyEq a b

と断られる。逆に言えば、それだけの違いしかない。

10. 型検査が証明の検査になる

前節の見方から、この教材の中心の主張が出る。

証明は項なのだから、「証明が正しいか」は「項が主張どおりの型を持つか」という 型検査の問題になる。型検査は機械的な計算であり、Lean はすべての宣言に対してそれを実行している。だから、ファイルがエラーなしに受理された時点で、そこに書かれた全定理の検査は済んでいる。

ただし2つ、但し書きがある。第一に、この検査は宣言済みの公理に相対的である。 axiom bad : False のような宣言もエラーなく受理できてしまうので、「何を公理として使ったか」は #print axioms で別に監査する必要がある。第二に、証明を保留する印 sorry はエラーではなく警告になる（依存すると #print axioms に sorryAx が現れる）。だから正確には、「エラーがなく、sorry の警告もなく、#print axioms の結果が納得できる公理だけ」を見る。Top.lean の末尾で、主定理に対してこの監査を実行する。

正確には: エラボレータとカーネル

ここまで「型検査」と一括りに呼んできた処理は、正確には2段階に分かれている。

ソースコード
  → エラボレータ: 記法を展開し、省略された引数（暗黙引数・インスタンス引数）を
    埋め、タクティク（`Top.lean` 1節）を実行して、省略のない項を組み立てる
  → カーネル: 完成した項の型を、小さな規則集だけで検査する

賢い処理はすべて前段のエラボレータに、信頼はすべて後段のカーネルにある。この分業のおかげで、前段がどれだけ複雑でも——記法が凝っていても、インスタンス探索が連鎖しても、タクティクが長大でも——誤った項が組み上がればカーネルが拒否する。証明の信頼性を支えているのは、エラボレータの賢さではなくカーネルの単純さである。これまで「型検査が暗黙引数を埋める」のように言ってきた箇所も、正確にはエラボレータの仕事である。

この2段構えが仮定の飛ばしをどう捕まえるのかを、数学でよくある誤りで見ておく。 補題を使うとき、その仮定の確認が甘いという誤りである。

例えば n - 1 + 1 = n は一見明らかに見える。ライブラリには Nat.sub_add_cancel : m ≤ n → n - m + m = n という補題があるから、これを当てて済ませたくなる。仮定 1 ≤ n は「明らか」なので穴 _ のままにしておくと:

example : ∀ n : Nat, n - 1 + 1 = n := fun n => Nat.sub_add_cancel _

error: don't know how to synthesize placeholder for argument `h`
context:
n : Nat
⊢ 1 ≤ n

このエラーを出したのは、2段構えの前段——エラボレータ——である。省略された仮定は「未解決のゴール ⊢ 1 ≤ n」として露出し、それが埋まらない限り完成した項が組み上がらないので、カーネルに渡る前に止まる。そして実際、この仮定はどうやっても埋められない。自然数の引き算は 0 - 1 = 0 と切り捨てなので、n = 0 がこの主張の反例だからである。

#eval (0 : Nat) - 1 + 1
1

1 になる。n = 0 が反例であることの計算による確認

紙の上では「明らか」の一言で通ってしまう仮定の飛ばしが、 Lean では埋まらない穴として必ず現れる。仮定を使うにはその証明を項として差し出すしかない。穴が残ればエラボレータは項を完成させられず、仮にどこかで誤った項が組み上がったとしても、最後はカーネルが受理しない。これが「Lean が受理した＝証明が検証された」と考えてよい理由である。

穴は書くときの道具にもなる

いまの例では穴が事故として現れたが、逆用すると組み立ての道具になる。 0節の isEven_double を、証明を知らないつもりで書いてみる。まず引数だけ取って、残り全体を穴にする:

theorem isEven_double : ∀ n : Nat, IsEven (n + n) := fun n => _

error: don't know how to synthesize placeholder
context:
n : Nat
⊢ IsEven (n + n)

エラボレータが「残っている穴の型」を教えてくれている（⊢ の右が、いま作るべきものの型である）。型の頭が ∃ だから部品は ⟨ ⟩——証人だけ埋めて ⟨n, _⟩ と書けば、報告は ⊢ n + n = 2 * n に変わる。0節の4段の梯子は 読むための道具立てだったが、書くときは、この機械との対話で同じ梯子を一段ずつ降りていける。

なお、型検査が保証するのは「主張したことを証明した」ことまでで、「主張が意図した数学を言えている」ことは保証しない。この点は Top.lean の冒頭で扱う。

11. 対応のずれ

対応は完全ではない。証明は「あるかないか」だけが問題で中身は区別されない（同じ命題の2つの証明は等しいものとして扱われる）のに対し、項は中身が区別される。この差が、使うときに現れる。

依存和からは第一成分を取り出せるが、存在量化からは取り出せない。

型側: どの点だったかを取り出せる。

def sigmaFst {α : Type} {P : α → Type} (s : (a : α) × P a) : α := s.1

#check sigmaFst
sigmaFst {α : Type} {P : α → Type} (s : (a : α) × P a) : α

型側: 第二成分も取り出せる。型が第一成分に依存していることに注意。

def sigmaSnd {α : Type} {P : α → Type} (s : (a : α) × P a) : P s.1 := s.2

#check sigmaSnd
sigmaSnd {α : Type} {P : α → Type} (s : (a : α) × P a) : P s.fst
-- 命題側では、これは書けない:
--
--   def existsFst (h : ∃ a, Q a) : α := h.1
--
--   error: Invalid projection: Cannot project a value of non-propositional type
--     α
--   from the expression
--     h
--   which has propositional type
--     ∃ a, Q a
--
-- 証明から値を取り出せてしまうと、中身を区別しないはずの証明が

-- 証人という中身を持つ命題の証明から、命題でないものを取り出すことを
-- 許していない。

ただし例外もある。False や Eq の証明は、命題でない型への分解にも使える。 5節の False.elim や等式によるデータの書き換えは、その例である。

補足（初読は飛ばしてよい）: 除去制限の例外

False にはそもそも証明がなく、取り出しで矛盾は起きない。 Eq の構成子は1つで、中身の区別は生じない。だから命題でないものへも分解できる:

#check @False.elim   -- @False.elim : {C : Sort u_1} → False → C

Prop の世界から Type の世界へ渡れている。5節から使ってきた .elim や、等式によるデータの書き換え（▸、Top.lean で使用）が正当なのはこのためである。

これでこのファイルの仕事——対応を作り、検査の正体を見届けること——は終わりである。なお Lean には、証明を命令の列で書くもう1つの流儀（タクティク）があり、Top.lean の実戦ではそちらが主体になる。紹介はTop.lean 1節で行う。
