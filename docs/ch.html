型と命題の対応（Curry–Howard 対応）の雰囲気

Lean には「型の世界」と「命題の世界」があり、この2つはよく似ている。

  • 型 α に対しては、項 a : α を作る。
  • 命題 p に対しては、証明 h : p を書く。

型の世界での基本の活動は項を作ること、命題の世界での基本の活動は証明を書くこと。このファイルで伝えたいのは、2つの世界の類似に基づいて、 ある型の項を作ることと、ある命題の証明を書くことを対応させられるということ。

それを見るために、すでにある型（命題）から新しい型（命題）を作る操作を6つ並べ、それぞれについて「どう作るか（導入）」と「どう使うか（除去）」を見比べる。対応する項と証明が同じ字面で書けることが繰り返し現れる。

型命題
関数α → βp → q（ならば）
積α × βp ∧ q（かつ）
和α ⊕ βp ∨ q（または）
空EmptyFalse（⊥）
依存積(a : α) → P a∀ a, Q a
依存和(a : α) × P a∃ a, Q a
universe u v w

1. 関数型と「ならば」

導入: fun x => e で作る。x : α を仮に置いて e : β を作れば α → β が得られる。「p を仮定すれば q が示せる」なら p → q が言える、というのと同じ形。

除去: f a と適用する。関数に項を与えれば値が出る。含意に証明を与えれば結論の証明が出る。

/-- 型側の導入: `β` の項が1つあれば、`α` から `β` への関数が作れる。 -/
def constFun (b : β) : α → β := fun _ => b

#check constFun

/-- 命題側の導入: `q` の証明が1つあれば、`p → q` が示せる。字面はまったく同じ。 -/
theorem constImp (hq : q) : p → q := fun _ => hq

#check constImp

/-- 型側の除去: 適用。 -/
def applyFun (f : α → β) (a : α) : β := f a

#check applyFun

/-- 命題側の除去: 適用。これも字面が同じ。 -/
theorem applyImp (h : p → q) (hp : p) : q := h hp

#check applyImp

-- ここまで型側を `def`、命題側を `theorem` で書いたが、どちらの宣言も
-- 「コロンの右に書いたものを持つ項を、`:=` の右に差し出す」という同じ形をしている。
-- `theorem` とは「命題という型の項（＝証明）を作る `def`」にほかならない。
-- 以下のすべての対でも、この形は変わらない。

✏ 練習

型側と命題側を同じ字面で書けることを、自分の手で確かめる。

  1. 「2回適用」を両方の世界で書け: def apply2 : (α → α) → α → α と theorem applyTwice : (p → p) → p → p。
  2. 「A より B、B より C」の連鎖 theorem chain : (p → q) → (q → r) → p → r を項で書け。

2. 直積型と「かつ」

導入: ⟨a, b⟩ で作る。両方の成分を揃えれば組が作れる。 p の証明と q の証明を揃えれば p ∧ q の証明になる。

除去: .1 と .2 で取り出す。組からは各成分が取れる。 p ∧ q からは p も q も取れる。

def mkProd (a : α) (b : β) : α × β := ⟨a, b⟩

#check mkProd

theorem mkAnd (hp : p) (hq : q) : p ∧ q := ⟨hp, hq⟩

#check mkAnd

/-- 型側: 組を入れ替える。 -/
def swapProd : α × β → β × α := fun x => ⟨x.2, x.1⟩

#check swapProd

/-- 命題側: 「かつ」を入れ替える。`swapProd` と一字一句同じ証明項で書ける。 -/
theorem swapAnd : p ∧ q → q ∧ p := fun h => ⟨h.2, h.1⟩

#check swapAnd

✏ 練習

  1. theorem and_left : p ∧ q → p と型側の対応物 def fst' : α × β → α を書き比べよ。
  2. theorem and_assoc' : (p ∧ q) ∧ r → p ∧ (q ∧ r) を ⟨…⟩ と .1 .2 で書け。

3. 直和型と「または」

導入: .inl か .inr のどちらかで作る。左右どちらかの成分があればよい。 p の証明があれば p ∨ q が言えるし、q の証明でもよい。

除去: 場合分け（match）。和の項を使うには、左のときと右のときの両方について行き先を用意する必要がある。「または」を使うときに場合分けするのと同じ。

def inlSum (a : α) : α ⊕ β := .inl a

#check inlSum

theorem inlOr (hp : p) : p ∨ q := .inl hp

#check inlOr

/-- 型側: 和を入れ替える。左なら右へ、右なら左へ。 -/
def swapSum : α ⊕ β → β ⊕ α := fun x =>
  match x with
  | .inl a => .inr a
  | .inr b => .inl b

#check swapSum

/-- 命題側: 「または」を入れ替える。これも同じ形の場合分けで書ける。 -/
theorem swapOr : p ∨ q → q ∨ p := fun h =>
  match h with
  | .inl hp => .inr hp
  | .inr hq => .inl hq

#check swapOr

/-- 型側の除去を一般の形で書いたもの。 -/
def elimSum : α ⊕ β → (α → γ) → (β → γ) → γ := fun x f g =>
  match x with
  | .inl a => f a
  | .inr b => g b

#check elimSum

/-- 命題側の除去。`Or.elim` と同じもの。字面は上と同じ。 -/
theorem elimOr : p ∨ q → (p → r) → (q → r) → r := fun h f g =>
  match h with
  | .inl hp => f hp
  | .inr hq => g hq

#check elimOr

✏ 練習

  1. theorem or_idem : p ∨ p → p を match で書け（どちらの札でも中身は同じ）。
  2. theorem or_map : (p → q) → p ∨ r → q ∨ r を書け（札を見て、左のときだけ関数を適用する）。

4. 空の型と「⊥」

項が1つもない型が Empty、証明が1つもない命題が False。

導入: ない。これが空であることの意味そのもので、作り方が用意されていないから項（証明）が存在しない。

除去: 場合分けすべき場合が1つもないので、「もし項が手に入ったなら何でも作れる」という形になる。矛盾からは何でも従う、というのと同じ。

/-- 型側: `Empty` の項があれば何の型の項でも作れる。 -/
def elimEmpty : Empty → α := fun e => e.elim

#check elimEmpty

/-- 命題側: 矛盾からは何でも従う。 -/
theorem elimFalse : False → p := fun h => h.elim

#check elimFalse

/-- 否定 `¬p` は `p → False` のことなので、実は新しい作り方ではない。 -/
theorem notIntro (h : p → False) : ¬p := h

#check notIntro

✏ 練習

  1. theorem noContra : p → ¬p → q を書け。ヒント: ¬p は p → False なので、適用すると False が出る。あとは .elim。
  2. theorem dni : p → ¬¬p を書け（二重否定の導入。ほとんど1語で書ける）。書けたら、逆向き ¬¬p → p にも挑戦して、書けないことを確かめよ。なぜ書けないか（そしてどう書くか）は Top.lean の公理の節で分かる。

5. 依存積と「すべての」

関数型 α → β を一般化して、行き先の型が入力ごとに変わってよいことにしたのが依存積 (a : α) → P a。P : α → Type v は「α の各点に型を割り当てるもの」。

命題側で対応するのは全称量化 ∀ a, Q a。 Q : α → Prop は「α の各点に命題を割り当てるもの」で、形はまったく同じ。

導入・除去: 関数のときと変わらず fun x => e と f a。 α → β は P が定数のときの特別な場合なので、これは自然なこと。

variable {P : α → Type v} {Q : α → Prop}

def mkPi (f : (a : α) → P a) : (a : α) → P a := fun a => f a

#check mkPi

theorem mkForall (h : ∀ a, Q a) : ∀ a, Q a := fun a => h a

#check mkForall

/-- 型側の除去: 点 `a` を与えると `P a` の項が出る。 -/
def applyPi (f : (a : α) → P a) (a : α) : P a := f a

#check applyPi

/-- 命題側の除去: 点 `a` を与えると `Q a` の証明が出る。 -/
theorem applyForall (h : ∀ a, Q a) (a : α) : Q a := h a

#check applyForall

✏ 練習

  1. theorem all_and {R : α → Prop} : (∀ a, Q a) → (∀ a, R a) → ∀ a, Q a ∧ R a を書け（各点で証明を組にするだけ）。

6. 依存和と「存在する」

直積 α × β を一般化して、第二成分の型が第一成分に依存してよいことにしたのが依存和 (a : α) × P a。命題側で対応するのが存在量化 ∃ a, Q a。

導入: ⟨a, b⟩。「どの点か」と「その点で成り立つこと」を組にする。存在を示すには、実際に点を1つ挙げて、それが条件を満たすことを言えばよい、というのと同じ。

除去: 組を分解する。型側は .1 .2 で取り出せる。命題側にはここだけ制限があるので、後の 11 節で見る。

def mkSigma (a : α) (b : P a) : (a : α) × P a := ⟨a, b⟩

#check mkSigma

theorem mkExists (a : α) (h : Q a) : ∃ a, Q a := ⟨a, h⟩

#check mkExists

/-- 型側: 組を受け取る関数は、2引数の関数と同じこと（カリー化）。 -/
def currySigma : (((a : α) × P a) → γ) → ((a : α) → P a → γ) :=
  fun f a b => f ⟨a, b⟩

#check currySigma

/-- 命題側: 「存在するなら `r`」は「どの点についても、条件を満たすなら `r`」と同じこと。
`currySigma` と同じ証明項で書ける。 -/
theorem curryExists : ((∃ a, Q a) → r) → (∀ a, Q a → r) :=
  fun f a b => f ⟨a, b⟩

#check curryExists

✏ 練習

  1. theorem exists_map {R : α → Prop} : (∀ a, Q a → R a) → (∃ a, Q a) → ∃ a, R a を書け（証人はそのまま、根拠だけ差し替える）。

7. 導入と除去のまとめ

作り方（導入）と使い方（除去）を並べると、左右で同じ形をしていることが見える。

型命題導入除去
関数α → βp → qfun x => ef a
積α × βp ∧ q⟨a, b⟩.1 / .2
和α ⊕ βp ∨ q.inl / .inrmatch で場合分け
空EmptyFalseなし.elim
依存積(a : α) → P a∀ a, Q afun x => ef a
依存和(a : α) × P a∃ a, Q a⟨a, b⟩.1 / .2、match

導入は「その型（命題）を作るのに何が要るか」、除去は「その型（命題）を持っているとき何が言えるか」。上の例で見たとおり、対応する両側は多くの場合まったく同じ字面で書ける。

字面が同じになるのは偶然ではない。証明を書くときにしていることは、関数を書き、組を作り、場合分けをすること——つまり項の構成そのものである。「命題 p を証明する」とは「p を型とみなして、その項を1つ作る」ことであり、この対応が Curry–Howard 対応と呼ばれるものである。

/-- 型側と命題側で同じ項が通ることの確認。
`⟨x.2, x.1⟩` という同じ式が、片方では組の入れ替え、
もう片方では「かつ」の入れ替えの証明になっている。 -/
example : α × β → β × α := fun x => ⟨x.2, x.1⟩

example : p ∧ q → q ∧ p := fun x => ⟨x.2, x.1⟩

8. 例: 自然数の命題を構成子で証明する

「命題を証明する＝項を作る」を、自然数のいちばん基本的な命題で確かめておく。鍵は、= や ≤ といった命題を作るもの自体が、Intro.lean の MyNat などと同じく帰納型として定義されていることである。

等しさ Eq

a = b は Eq a b の記法で、Eq は構成子を1つだけ持つ帰納型である:

inductive Eq {α : Sort u} : α → α → Prop
  | refl (a : α) : Eq a a

構成子 refl が作れるのは、両辺が同じ Eq a a の形の項だけ。「a = a はいつでも証明できて、それが等しさの証明のすべて」というのが、等しさの定義そのものになっている。

example : 0 = 0 := Eq.refl 0
example : 0 = 0 := rfl        -- 略記。引数の `0` は型 `0 = 0` の側から決まる

一方 0 = 1 という型の項は refl では作れず、実際この型に項は存在しない。証明のない命題は、項のない型 Empty（4節）と同じ立場にある。

Intro.lean で 1 + 1 = 2 まで rfl で証明できたのは、型検査が両辺を 計算してから比べるからである。1 + 1 は計算すると 2 になるので、 1 + 1 = 2 は 2 = 2 と同じ型であり、refl の射程に入る。

順序 Nat.le

m ≤ n も帰納型の記法で、こちらは構成子が2つある:

inductive Nat.le (n : Nat) : Nat → Prop
  | refl : Nat.le n n
  | step {m} : Nat.le n m → Nat.le n (succ m)   -- `succ m` は `m + 1`

作り方は「n ≤ n」と「n ≤ m が作れているなら n ≤ m + 1 も作れる」の2通り。つまり ≤ の証明は、refl から出発して step を必要な回数だけ重ねた項である。 zero に succ を重ねて自然数を作るのと、まったく同じ手つきで証明が作れる。

example : 0 ≤ 0 := Nat.le.refl
example : 0 ≤ 1 := Nat.le.step Nat.le.refl
example : 0 ≤ 2 := Nat.le.step (Nat.le.step Nat.le.refl)

これが7節の主張の実演である。0 ≤ 2 を証明するとは、帰納型 Nat.le の項を構成子から組み立てることに他ならず、出来上がった証明はデータと同じ資格でそこにある。∧ ∨ ∃ False も同様に帰納型として定義された命題であり（2〜4節、6節）、導入で使った ⟨_, _⟩ や .inl は、それらの構成子だったのである。

等式の法則は公理ではない

ふつうの述語論理では、等式の反射律や代入原理は論理に組み込まれた公理である。 Lean では違う。いま見たとおり Eq はただの帰納型の宣言で、等式に期待される振る舞いは、そこから実際に出てくる:

  • 反射律は構成子 refl そのもの
  • 代入原理（a = b なら、P a の証明から P b の証明が得られる）は、帰納型の宣言を受理したときに Lean が自動生成する帰納法原理 Eq.rec そのもの
  • 対称律・推移律・合同性は、そこから証明される定理
#print axioms Eq.symm   -- 'Eq.symm' does not depend on any axioms

つまり Lean の基礎にあるのは等式の公理のリストではなく、「（健全性の条件を満たす）帰納型の宣言に対して、構成子・帰納法原理・計算規則を与える」という一般規則のほうである。等式に限らず、この教材に出てくる ∧ ∨ ∃ = ≤ の論理法則はすべて、依存関数型・宇宙・帰納型という土台から定義と定理として出てくる。

例外、すなわち土台の外から公理として足されているものは、外延性・選択の類の 3つだけで、それは Top.lean の末尾で #print axioms により確認する。

実験: 等式をもう1つ作る

Eq が特別な組み込みでないことは、実際に作り直してみるとよく分かる。同じ形の帰納型 MyEq を宣言すると、帰納法原理も同じ形で自動生成される。

inductive MyEq {α : Sort u} (a : α) : α → Prop where
  | refl : MyEq a a

#check MyEq

/-- 対称律は帰納法原理（`cases`）だけで導ける。推移律や代入原理も同様。 -/
theorem MyEq.symm {a b : α} (h : MyEq a b) : MyEq b a := by
  cases h
  exact .refl

#check MyEq.symm

/-- 型検査が両辺を計算してから比べる仕組みも `Eq` 専用ではないので、
`1 + 1 = 2` に当たる命題はやはり構成子だけで証明できる。 -/
example : MyEq (1 + 1) 2 := .refl

/-- しかも、`Eq` と同値であることを系の中で証明できる。
両方向とも「相手の帰納法原理で場合分けして、自分の構成子を置く」だけ。 -/
theorem myEq_iff_eq {a b : α} : MyEq a b ↔ a = b :=
  ⟨fun h => by cases h; rfl, fun h => by cases h; exact .refl⟩

#check myEq_iff_eq

/-- `propext`（`Top.lean` の3公理の1つ）まで使えば、命題として等しいことになる。 -/
example {a b : α} : MyEq a b = (a = b) := propext myEq_iff_eq

つまり2つ目の等式を作っても、衝突も分裂も起きず、同じものが増えるだけである。 Eq に残る特別さは論理の側にはなく、道具立ての側にある: = という記法や rw・simp などのタクティクは Eq に向けて作られているので、 MyEq では使えない。例えば h : MyEq a b で rw [h] とすると

error: Invalid rewrite argument: Expected an equality or iff proof
or definition name, but `h` is a proof of MyEq a b

と断られる。逆に言えば、それだけの違いしかない。

✏ 練習

  1. example : 1 ≤ 3 を Nat.le の構成子だけで書け（step は何回要るか）。
  2. 本文の MyEq.symm にならって、MyEq.trans を自分で証明せよ（h₂ を cases すれば h₁ がそのまま答えになる）。

9. 証明を読んで納得するとは何をすることか

数学の証明は、書かれ、読まれ、読んだ人が「正しい」と納得することで機能する。では、証明を読んで納得するとき、読者は何をしているのだろうか。

こうモデル化できる。読者は文脈——いま使ってよいものの一覧（定理の仮定・既知の定理・ここまでに導いた事実）——を持って読み進める。そして各文で、次のような確認をしている。

  • 「〜とする」「任意に取る」— 新しい変数や仮定を文脈に加える
  • 「A と B より C」— A と B が文脈にあるか、当てはめの条件が合うかを確かめて、C を文脈に加える
  • 「〜となる x を取る」— 文脈にある存在文を分解して、x とその性質を文脈に加える
  • 最後の文 — 示すべきことが、文脈にあるものから組めているかを確かめる

重要なのは、どの確認も局所的だということである。見るのはその一文と現在の文脈だけでよく、証明全体の狙いや発想を理解する必要はない。しかも確認の中身は「一覧にあるか」「形が合うか」の照合であって、機械的に実行できる。直感や洞察が要るのは証明を見つけるときであって、検める作業には要らない。「納得した」とは、この検査がすべての文で通ったことの別名である。

以下、初等的な事実を3つ、この観点で書いてみる。それぞれについて「ふつうの証明」「省略をすべて書き出した詳細版」「Lean の項」を並べる。詳細版の各文に番号を振り、項の対応する部分に同じ番号を添えるので、 詳細化を進めていった先に項があることを見比べてほしい。

/-- 偶数であること: 半分になる数が存在する。 -/
def IsEven (n : Nat) : Prop := ∃ k, n = 2 * k

#check IsEven

例1: どの n についても n + n は偶数

ふつうの証明。「n + n = 2n だから偶数である。∎」

詳細版。

  1. n を任意に取る。
  2. 既知の定理 Nat.two_mul n : 2 * n = n + n の左右を入れ替えて、 n + n = 2 * n を得る。
  3. よって「半分」の証人として n が取れ、n + n は偶数である。∎
theorem isEven_double : ∀ n : Nat, IsEven (n + n) :=
  fun n =>                     -- (1) n を任意に取る（∀ の導入）
    ⟨n, (Nat.two_mul n).symm⟩  -- (3) 証人は n、(2) 根拠は two_mul の対称形（∃ の導入）

#check isEven_double

例2: 単射どうしの合成は単射

ふつうの証明。「g (f x) = g (f y) とすると、g の単射性より f x = f y。 f の単射性より x = y。∎」

詳細版。

  1. x, y を任意に取り、h : g (f x) = g (f y) を仮定する。
  2. 仮定 hg は「任意の u, v について、g u = g v ならば u = v」という全称文である。 u := f x、v := f y と特殊化して h に適用すると、f x = f y を得る。
  3. 仮定 hf を同様に f x = f y に適用して、x = y を得る。これが示すべきことだった。∎
theorem comp_injective {f : α → β} {g : β → γ}
    (hg : Function.Injective g) (hf : Function.Injective f) :
    Function.Injective (fun x => g (f x)) :=
  fun x y h =>             -- (1) x, y を取り、h を仮定する
    hf (hg h : f x = f y)  -- (2) hg を h に適用（型注釈は「f x = f y を得る」の写し）
                           -- (3) その結果に hf を適用

#check comp_injective

ふつうの証明にある「〜の単射性より」という一語が、項では適用 hg h そのものになっている。「より」＝「文脈にある全称文・含意文への適用」である。また、全称文の特殊化（u := f x など）を読者は無意識にやっているが、項では暗黙引数の解決として型検査器が同じことをやっている。

例3: 偶数と偶数の和は偶数

ふつうの証明。「n = 2k、m = 2l と書けば n + m = 2k + 2l = 2(k + l)。∎」

詳細版。今度は文脈が増えていく様子も〔 〕に添える。最初の文脈は n m : Nat、hn : IsEven n、hm : IsEven m である。

  1. hn は存在文なので、n = 2 * k となる k を取り、等式を hk と名付ける。〔文脈に k と hk が加わる〕
  2. 同様に hm から l を取り、等式を hl と名付ける。〔文脈に l と hl〕
  3. hk の両辺に右から m を足して、h1 : n + m = 2 * k + m を得る。〔文脈に h1〕
  4. hl の両辺に左から 2 * k を足して、h2 : 2 * k + m = 2 * k + 2 * l を得る。〔文脈に h2〕
  5. 分配法則より、h3 : 2 * k + 2 * l = 2 * (k + l)。〔文脈に h3〕
  6. h1・h2・h3 を「= のつながり」として読めば、n + m = 2 * (k + l)。
  7. よって証人 k + l により、n + m は偶数である。∎

ふつうの証明の「n + m = 2k + 2l = 2(k + l)」という等式の列は、詳細版では 3〜6 に展開された。紙で「= を続けて書く」ことの正体は、「両辺に同じ操作を施す」（congrArg——8節で公理でなく定理だと確かめたもの）と「= をつなぐ」（Eq.trans）の繰り返しである。

theorem isEven_add {n m : Nat} (hn : IsEven n) (hm : IsEven m) : IsEven (n + m) :=
  have ⟨k, hk⟩ := hn                                                  -- (1)
  have ⟨l, hl⟩ := hm                                                  -- (2)
  have h1 : n + m = 2 * k + m := congrArg (· + m) hk                  -- (3)
  have h2 : 2 * k + m = 2 * k + 2 * l := congrArg (2 * k + ·) hl      -- (4)
  have h3 : 2 * k + 2 * l = 2 * (k + l) := (Nat.mul_add 2 k l).symm   -- (5)
  ⟨k + l, (h1.trans h2).trans h3⟩                                     -- (7) 証人と (6) つないだ等式

#check isEven_add

種明かし: have も適用である

例3で使った have はタクティクではなく項の構文で、しかもただの略記である:

have h : C := e
続き

は (fun h : C => 続き) e と同じ項になる。つまり「C を得た。以下それを使う」という詳細版の文型は、「C の証明 e を、C を仮定した続きに渡す」という 関数適用だった。存在文の分解 have ⟨k, hk⟩ := … も match の略記である。詳細版の一文一文は、最初から項の部品だったことになる。

まとめ: 読者と型検査器は同じ仕事をしている

ふつうの証明 → 詳細版 → 項、と進むにつれて増えたのは省略の穴埋めだけで、新しい種類の思考は何も足していない。形式化とは翻訳ではなく、詳細化の極限である。

そして、詳細版の各文に読者が行う局所的な照合——「文脈にあるか」「形が合うか」——を、一行も飽きず、一箇所も「まあいいか」と流さずに実行するものこそ、次節で見る型検査器である。逆に、型検査を通る形に書けた証明は、同じ手順をたどれば人間も必ず検証できる。

最後に、紙の常套句と項の対訳をまとめておく。

紙の常套句項での正体
「〜とする」「任意に取る」fun（→・∀ の導入）
「A と B より C」適用（含意・全称文の除去）
「C を得た。以下それを使う」have h : C := …
「〜となる x を取る」have ⟨x, hx⟩ := …（∃ の分解）
「求めるものは〜である」⟨証人, 根拠⟩（∃ の導入）
「場合分けする」match（∨ などの除去）
「両辺に〜を施す」「= をつなぐ」congrArg・Eq.trans
「明らか」rfl（計算で両辺が一致するときだけ書ける）
「∎」型検査が通ること

10. 型検査が証明の検査になる

前節の見方から、この教材の中心の主張が出る。

証明は項なのだから、「証明が正しいか」は「項が主張どおりの型を持つか」という 型検査の問題になる。型検査は機械的な計算であり、Lean はすべての宣言に対してそれを実行している。だから、ファイルがエラーなしに受理された時点で、そこに書かれた全定理の検査は済んでいる。

型検査が何を捕まえるのかを、数学でよくある誤りで見ておく。 補題を使うとき、その仮定の確認が甘いという誤りである。

例えば n - 1 + 1 = n は一見明らかに見える。ライブラリには Nat.sub_add_cancel : m ≤ n → n - m + m = n という補題があるから、これを当てて済ませたくなる。仮定 1 ≤ n は「明らか」なので穴 _ のままにしておくと:

example : ∀ n : Nat, n - 1 + 1 = n := fun n => Nat.sub_add_cancel _

error: don't know how to synthesize placeholder for argument `h`
context:
n : Nat
⊢ 1 ≤ n

Lean は、埋められていない仮定 1 ≤ n を名指しで要求してくる。そして実際、この仮定はどうやっても埋められない。自然数の引き算は 0 - 1 = 0 と切り捨てなので、n = 0 がこの主張の反例だからである。

#eval (0 : Nat) - 1 + 1   -- 1 になる。`n = 0` が反例であることの計算による確認

紙の上では「明らか」の一言で通ってしまう仮定の飛ばしが、型検査では埋まらない穴として必ず現れる。仮定を使うにはその証明を項として差し出すしかなく、検査器は穴の残った項を受理しない。これが「Lean が受理した＝証明が検証された」と考えてよい理由である。

なお、型検査が保証するのは「主張したことを証明した」ことまでで、「主張が意図した数学を言えている」ことは保証しない。この点は Top.lean の冒頭で扱う。

✏ 練習

  1. n + 1 - 1 = n は（n - 1 + 1 = n と違って）すべての n で正しい。 #check @Nat.add_sub_cancel でライブラリの補題の形を調べ、これを使って example : ∀ n : Nat, n + 1 - 1 = n を証明せよ。今度は穴が残らないことを確かめること。

11. 対応のずれ

対応は完全ではない。証明は「あるかないか」だけが問題で中身は区別されない（同じ命題の2つの証明は等しいものとして扱われる）のに対し、項は中身が区別される。この差が、除去のところに現れる。

依存和からは第一成分を取り出せるが、存在量化からは取り出せない。

/-- 型側: どの点だったかを取り出せる。 -/
def sigmaFst (s : (a : α) × P a) : α := s.1

#check sigmaFst

/-- 型側: 第二成分も取り出せる。型が第一成分に依存していることに注意。 -/
def sigmaSnd (s : (a : α) × P a) : P s.1 := s.2

#check sigmaSnd

-- 命題側では、これは書けない:
--
--   def existsFst (h : ∃ a, Q a) : α := h.1
--
--   error: Invalid projection: Cannot project a value of non-propositional type α
--          from the expression h which has propositional type ∃ a, Q a
--
-- 証明から値を取り出せてしまうと、中身を区別しないはずの証明が
-- 計算に影響することになってしまう。そこで Lean は、
-- 命題の証明を分解して**命題でないもの**を作ることを許していない。

/-- 結論が命題である限り、分解して使うことはできる。
`∃` の除去はこの形になる。 -/
theorem existsElim (h : ∃ a, Q a) (hr : ∀ a, Q a → r) : r :=
  match h with
  | ⟨a, ha⟩ => hr a ha

#check existsElim

-- 「または」でも事情は同じ。どちらだったかを `Bool` として取り出そうとすると:
--
--   def orToBool (h : p ∨ q) : Bool :=
--     match h with
--     | .inl _ => true
--     | .inr _ => false
--
--   error: recursor `Or.casesOn` can only eliminate into `Prop`
--
-- 「`Prop` にしか落とせない」というのがまさに制限の内容で、
-- 3 節の `swapSum` が型側では書けて、`swapOr` が命題側でも書けたのは、
-- どちらも行き先が同じ世界（型なら型、命題なら命題）に留まっていたから。

/-- 結論が命題であれば、「または」も場合分けして使える。 -/
theorem orElimToProp (h : p ∨ q) (f : p → r) (g : q → r) : r := h.elim f g

#check orElimToProp

12. タクティク — 証明のもう1つの書き方

ここまで、証明はすべて項として直接書いてきた。Lean にはもう1つの流儀があり、 by に続けて、項を組み立てる命令（タクティク）の列を書く。 2節の swapAnd をタクティクで書き直してみる。

theorem swapAnd' : p ∧ q → q ∧ p := by
  intro h            -- `fun h =>` に対応
  exact ⟨h.2, h.1⟩   -- この項をそのまま置く

#check swapAnd'

intro は fun、exact は項そのものに対応していて、どちらの流儀でも最終的に出来上がるのは同じ項である。つまりタクティクは証明そのものではなく、項を組み立てるためのメタなプログラムであり、 by ブロックは実行されると項を生成する。検査されるのはあくまで生成された項のほう。生成結果は #print で見られる:

#print swapAnd'
-- 表示: `theorem swapAnd' : ∀ {p q : Prop}, p ∧ q → q ∧ p := fun {p q} h => ⟨h.right, h.left⟩`
-- タクティクが生成した項は、2節で手書きした `swapAnd` と同じものである。

だから10節の話はそのまま当てはまる: タクティクで書いた証明も、出来上がった項が型検査を通ることで検証される。

このファイルは対応を見るために項を直接書いてきたが、Top.lean は証明が長いのでタクティク主体で書かれている。出てくるものの早見表:

  • intro h — 仮定を1つ取り込む（fun h =>）
  • exact e — 項 e でゴールを閉じる
  • refine ⟨?_, ?_⟩ — 項の穴 ?_ を残して置き、穴を続きのゴールにする
  • apply f — 結論から逆向きに f を適用し、引数をゴールとして残す
  • constructor — ゴールの型の構成子を適用する
  • cases h with … — 帰納型の項 h を場合分けする（match に対応）
  • rw [heq] — 等式 heq でゴールを書き換える
  • show t — ゴールを定義上等しい形 t に読み替える
  • have h : t := e — 補助的な項に名前を付けて続ける
  • by_cases h : p — p が成り立つ場合と否定の場合に分ける（古典論理）

✏ 練習

  1. swapOr をタクティク（intro・cases・exact）で書き直し、 #print で生成された項を本文の swapOr と見比べよ。
