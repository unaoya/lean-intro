## 背景と目的

現行の順序は Intro1（約1970行）→ CH（約1870行）。Intro1 に時間がかかると、
教材の核である「型検査が証明の検査になる」に入るのが遅れる。

Intro1 と CH をそれぞれ3分割して交互に読む構成にすれば、証明チェックの核心に
現行 Intro1 の約4割（§1〜§3、約810行）で到達できる。さらに、新しい型の作り方を
1つ学ぶごとに対応する論理が1つ手に入るので、「型の作り方と論理の対応」という
教材の核がファイルの並びそのものに現れる。

## 論理と型の部品の依存関係

| 論理 | 必要な Intro1 の部品 |
|---|---|
| ならば | §1 項と型、§2 def、§3 関数 |
| かつ・または・矛盾 | §4 帰納型、§5 structure |
| 存在（依存和） | §3 型を返す関数（述語）、§4 `match`、§5 依存するフィールド・無名構成子 |
| 全称（依存積） | §6 依存関数型 |

存在は §6 を必要としない（依存するフィールドを持つ組は §5 の補足で導入済み）。
§6 が本当に必要なのは、全称 `∀` の型の側だけである。
暗黙引数 `{ }` は §4（`MySum.inl`）で導入されている。

## 各 CH ファイルの中身（現行 CH.lean からの出典）

### CH1 — ならば

- 冒頭の主張（命題そのものが型、その項を作ることが証明）
- §0「命題と証明の書き方」、例1 modus ponens、例2 含意の推移（練習つき）
- §1 整理「命題・theorem・rfl」
- §2 整理「関数型とならば」
- §10 前半（型検査が証明の検査になる。公理と `sorry` の監査まで）
- 締め: 「ならばだけでも型検査で証明を検査できた」とまとめ、CH2・CH3 への見通しを示す

### CH2 — かつ・または・矛盾・存在

- §3 かつ、§4 または、§5 矛盾（`Empty`・`False`）
- 存在の小例（`exists_eq_two`、`IsEven 10 := ⟨5, rfl⟩`）。`IsEven` はここで定義する
- 存在を使う例: ∀ を含まない `exists_left`（`(∃ a, Q a ∧ R a) → ∃ a, Q a`）を
  現行 §7 の練習から本文に昇格させる
- §7 依存和のうち `mkSigma`・`mkExists`・部分型
- §9 自然数の命題（`Eq`・`≤` が帰納型であること、`noConfusion`、`MyEq`）。
  帰納型を学んだ直後なので、ここが最も自然

### CH3 — 全称と総仕上げ

- 全称の小例 `all_refl`、例 単射の合成、例 `n + n` は偶数、存在を使う `exists_map`、
  例 偶数の和、補足（`two_mul` を底まで）、例 全射の合成
- §6 整理「依存積とすべての」（`0 * n` の補足を含む）
- §7 の残り（`currySigma`・`curryExists`、`Fin`・`last`。どちらも依存関数を使う）
- §8 示すときと使うときのまとめ（§0 末尾の「頭の動きの一覧」をここに統合）
- §10 後半（エラボレータとカーネル、仮定の飛ばし、穴を書くときの道具にする）
- §11 対応のずれ（`existsElim` が仮定に ∀ を含むため）

## 付随する調整

1. **CH1 の中の小さな先取り**: 暗黙引数は Intro1 §4 で導入されるので、CH1 の時点では未出。
   §2 の `{α β : Type}`・`{p q : Prop}` は明示引数に書き換える。
   `theorem modus_ponens (P Q : Prop) …` は厳密には依存関数型だが、binder 形式の表示
   （§3 で既習）として読めるので本文はそのままでよい。ただし CH1 練習1の `#check` が出す
   `∀ (P Q : Prop), …` という表示には、一言の先取り注記が必要。
2. **Intro1 の先取り枠**: §1「先取り（CH）: 型の推測が証明の検証になる」は削除できる
   （直後に CH1 が来る。Issue #2 でも「先取りすぎ」と指摘あり）。
   §4 の CH 向け先取り枠（「全部」と「別々」、仮定として使う・結論として示す、
   構成子の単射性）は、次の CH2 ですぐ回収されるので短い予告に縮める。
3. **参照と解答**: refcheck は固定ラベルの見出しが実際にどのファイルにあるかで参照先を
   決めるので、節をファイル間で移してもラベルはそのままでよい。ファイル名と番号は自動で
   同期される。解答の SOL チャンクは、ラベルごと新しい解答ファイルへ移す。
4. **import の連鎖**: Intro1a ← Intro1b ← Intro1c、CH1 ← CH2 ← CH3。
   Intro2 は Intro1c と CH3 を import する。
5. **ビルドと生成**: lakefile の roots、`lean2html.py` の `CHAPTERS`・`SOL_FILES`・
   `ROLES`、`refs.SECTION_STARTS`（CH は0始まり）、index の構成説明を更新する。

## 未決定の論点

1. **ファイル名**: `Intro1a/b/c`・`CH1/2/3` のような連番か、内容名か。
   Lean のモジュール名では `Intro1.1` とは書けない（ドットは階層の区切り、数字始まり不可）。
2. **例「偶数の和」の置き場所**: 引数で書けるので CH2 にも置けるが、
   「論理式」の段が ∀n ∀m を使うので CH3 が素直（推奨: CH3）。
3. **4段の梯子の初出**: 上の推奨どおりなら CH3 の単射の例が初出。
   CH1・CH2 の例は軽い段構え（ふつう → 型を意識した版 → 項）のままにする。
4. **例の番号**: ファイルごとに振り直すか、CH1〜3 を通して通し番号にするか。

## 懸念とリスク

- **存在が全称より先に来る**: 現行 CH §0（全称の小例 → 存在の小例 → 組み合わせ）とは逆順になる。
  ∀ なしで書ける存在の例は具体的な数に限られ、CH2 の存在の例はやや素朴になる。
- **Intro1c が薄い**（約200行）。§6 と総まとめ練習だけになる。
- **CH §0 の物語の分断**: 例1〜6 の一続きの流れを CH1〜CH3 に割るので、
  CH2・CH3 の冒頭に「再開」の導入が必要になる。
- **ファイル数の増加**: 章が6本＋解答ファイルも増え、index の目次が長くなる。
