## 2. 型検査が証明の検査になる {#sec-CH.type-checking}

含意と全称、単射の合成で行った型の照合から、この章の中心の主張を確かめよう。

証明は項なのだから、「証明が正しいか」は「項が主張どおりの型を持つか」という
**型検査**の問題になる。型検査は機械的な計算であり、Lean はすべての宣言に対して
それを実行している。だから、ファイルがエラーなしに受理された時点で、
そこに書かれた全定理の検査は済んでいる。

この主張には但し書きが3つある。
第一は、この検査が**宣言済みの公理に相対的**であること。
`axiom bad : 0 = 1` のような宣言もエラーなく受理できてしまうので、
「何を公理として使ったか」は `#print axioms` で別に監査する必要がある。
第二は、証明を保留する印 `sorry` がエラーではなく**警告**になること
（依存すると `#print axioms` に `sorryAx` が現れる）。だから正確には、
「エラーがなく、`sorry` の警告もなく、`#print axioms` の結果が納得できる
公理だけ」を見る。`06_Topology.lean` の末尾で、主定理に対してこの監査を実行する。
第三は、この監査の例を見たあとで述べる。

-/

#print axioms modus_ponens

/-!
    'modus_ponens' does not depend on any axioms

この証明は追加の公理に依存していない。
-/

/-!
### その検査は、形式化したかったものの検査か

第三の但し書きは、公理や `sorry` の監査を済ませても残る。
型検査が確かめるのは「項が主張どおりの型を持つ」ことだけで、
**その型が、本当に確かめたかった主張であるか**は型検査の外側にある。
問題は3点に分けられる。

1. 形式化の問題。「単射どうしの合成は単射」という気持ちを
   `∀ x y, g (f x) = g (f y) → x = y` と書いたとき、式が気持ちを正しく写しているかは、
   書いた人が判断するほかない。
2. 実装の問題。エラボレータやカーネルにバグがあれば、誤った項を受理しうる。
   カーネルを小さく保ち、独立した検査器で再検査する対策はあるが、ゼロにはならない。
3. 理論の解釈の問題。`P → Q` をなぜ「`P` ならば `Q`」と読んでよいのか、
   型をなぜ集合のように扱ってよいのか。型検査を通った項が一貫した意味を持つ、
   という仮定がここにある。この仮定が正しければ、矛盾が導けないことも従う。

第3点について、Lean の理論（帰納型・宇宙の階層・`Prop`・後で見る公理を含む）を
ZFC に相対的に解釈するモデルは知られている。ただしそのためには、ZFC に
到達不能基数を（宇宙の階層の段ごとに1つずつ、可算無限個）加える必要があり、
これは ZFC より真に強い仮定である。
この教材では以後、これらを認めたうえで「エラーなしに受理された」ことを検査済みと呼ぶ。
-/

/-!
### 仮定を取り違えると、型が合わなくなる

含意の推移で、本来 `hPQ hP` を渡すべきところに `hP` を直接渡すとどうなるか。

    theorem bad_trans (P Q R : Prop) (hPQ : P → Q) (hQR : Q → R) : P → R :=
      fun hP => hQR hP

`hQR` が要求するのは Q の証明だが、渡した `hP` は P の証明である。
Lean はこの適用を型の不一致として拒否する。
紙の証明で「Q である」という一段を飛ばしたことが、そのまま引数の型の不一致になる。

### 省略を補う処理と、完成した項の検査

ソースの記法を展開し、暗黙引数などを補うのが**エラボレータ**である。
その後、完成した項が宣言どおりの型を持つかを**カーネル**が検査する。
補完の仕組みが賢いことと、出来上がった項が正しいことは、別に確かめられる。
詳しい例は [`04_Exists.lean` の8節](#sec-CH2.checking-details)で読む。

ここまでで、仮定や対象を受け取り、適用で進む証明を読めた。
次は `03_InductiveTypes.lean` で構成子と場合分けを学ぶ。`04_Exists.lean` では、それを使って
存在を含む証明を読み、全射の合成へ進む。
-/
